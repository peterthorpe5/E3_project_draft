1. EXECUTIVE SUMMARY: READ THIS FIRST

1.1 Project outcome
-------------------

The project has become a modular, restartable computational platform for
pan-plant E3-ligase discovery, evolutionary grouping, biological evidence
integration, ligandability assessment, conserved-pocket analysis, direct 3D
comparison, structure-guided chemistry hand-off and interactive review.

The immediate grant goal is to identify experimentally tractable plant E3
ligases and ligandable conserved pockets that can support development of a
plant PROTAC toolkit. The first experimental target context is MTF1, with wheat
as an important biological system. The software should remain reusable beyond
MTF1, wheat and the currently reviewed species panel.

The main workflow currently evaluates 1,972 evolutionary groups for the broad
Milestone 2 structural campaign. The applications now present the evidence in
grant-facing, scientifically cautious form rather than as an unqualified list
of predicted E3 ligases.

3. HIGH-LEVEL PROJECT GOALS
===============================================================================

3.1 Scientific goal
-------------------

Build a broadly useful plant PROTAC-enabling resource by identifying and
prioritising plant E3 ligases whose evolutionary conservation, biological
evidence, structural tractability and conserved ligandable pockets make them
credible candidates for experimental follow-up.

The computational work supports, but does not replace, human structural
review, ligand discovery, biochemical validation and in-plant functional
validation.


3.2 Resource goal
-----------------

Create a pan-plant E3 atlas/database which can answer:

    Which known or seed-linked E3 families have broad plant representation?
    Which evolutionary groups contain mandatory crop species?
    Which groups have credible E3-associated domain evidence?
    Which group members have usable expression evidence?
    Which proteins have reliable predicted structures and pockets?
    Are the selected pockets conserved in sequence position?
    Are corresponding pockets conserved in 3D position and local structure?
    Which groups supply plausible chemistry starting points?
    Which evidence is missing, negative, positive or not assessed?
    Which exact source row, identifier, sequence, model, pocket and residue
    mapping supports a recommendation?


3.3 Engineering goal
--------------------

The platform must be:

    modular;
    testable;
    restartable;
    species-count agnostic;
    auditable;
    configuration driven;
    safe on Slurm and on workstations;
    read-only at the application layer;
    explicit about missing data;
    suitable for later larger proteome panels;
    reproducible from checksummed inputs and immutable configurations.


3.4 Experimental translation goal
---------------------------------

The grant-level translation includes a first target context around MTF1 and
wheat, discovery of E3 binders/ligands and eventual biological validation of
induced degradation or related target-control outcomes. The computational
ranking should produce reviewable experimental starting points, not a claim
that a predicted cavity is already a validated ligand-binding site.

4. MILESTONES AND TIMELINE
===============================================================================

4.1 Eighteen-month outline
--------------------------

The working eighteen-month plan is:

Months 1-6

    mine controlled E3 seeds and complete proteomes;
    build candidate sequence neighbourhoods;
    reconcile evolutionary groups;
    quantify species breadth and mandatory-species representation;
    attach domain and expression evidence;
    produce an auditable Milestone 1 prioritisation.

Months 7-12

    expand structural coverage;
    predict and review ligandable pockets;
    assess pocket-region sequence conservation;
    perform direct 3D pocket-position and local-structure comparisons;
    produce chemistry-ready target/pocket hand-offs;
    pursue an MTF1 binder and supporting protein-production tools.

Months 7-18

    perform biological and biochemical validation;
    connect prioritised E3/pocket/ligand evidence to wheat-relevant experiments;
    refine selectivity and induced-degradation hypotheses;
    feed experimental results back into ranking and resource annotation.


4.2 Milestone 1: evolutionary and pre-structure prioritisation
--------------------------------------------------------------

Milestone 1 asks whether useful E3 candidate groups can be identified across
the selected plant panel using controlled seed discovery, evolutionary
grouping, taxonomic coverage, domain evidence and expression evidence.

The key pre-structure gates are normally:

    minimum target-species fraction:                         0.90
    minimum mandatory-species fraction:                      1.00
    minimum domain-supported assessed-species fraction:      0.80
    minimum expression-supported assessed-species fraction:  0.80

The denominator for domain or expression support uses assessed species where
that evidence is available. Unavailable annotation is not silently counted as
a negative.

Milestone 1 also retains sensitivity analyses, near misses and complete
exclusion reasons. The recorded primary result remains distinct from slider-
generated what-if lists.


4.3 Milestone 2: structural, pocket and chemistry readiness
-----------------------------------------------------------

Milestone 2 asks which candidate evolutionary groups have structurally
credible and conserved small-molecule starting space.

Important structural criteria include:

    structurally assessed state;
    structure confidence and usable models;
    fpocket/P2Rank pocket evidence;
    validated pocket-to-sequence coordinate mapping;
    conserved pocket-bearing sequence region;
    structurally supported species breadth;
    minimum selected-pocket druggability across assessed members;
    equivalent 3D pocket position;
    local pocket-structure conservation;
    agreement of the configured structural aligners;
    explicit not-assessed states.

The recorded all-member druggability gate is inclusive at 0.50. The apps have
a focused final-gate slider which varies only that requirement while holding
all other recorded gates fixed. It is a sensitivity analysis and does not
rewrite the recorded candidate authority.

The broad campaign covers 1,972 evolutionary groups. Its current run needs
diagnosis and safe resume after the August 2026 workflow failure described in
Section 20.


4.4 Milestone 3 / experimental continuation
-------------------------------------------

The next scientific layer is experimental:

    express and purify prioritised E3-related proteins or domains;
    validate pocket/ligand binding;
    establish biochemical activity and selectivity;
    develop or select an MTF1 binder;
    assemble suitable bifunctional molecules where justified;
    test target degradation and phenotype in relevant plant systems;
    use negative results as explicit evidence rather than silently discarding
    them.

The computational resource should ultimately accept experimentally confirmed,
negative and ambiguous annotations without overwriting the provenance of the
original predictions.

5. PETER'S STRICT, STANDING CODING REQUIREMENTS
===============================================================================

These are project requirements, not optional style suggestions.

5.1 General quality
-------------------

    Production quality is required.
    Code must be modular and maintainable.
    Every new function requires meaningful unit-test coverage.
    New publication boundaries require integration or end-to-end tests.
    Tests must test behaviour, failure modes and scientific contracts, not only
    whether a function returns something.
    Defensive validation is required at public boundaries.
    Fail clearly and early when an authority, schema or path is invalid.
    Never make missing data appear to be biological zero, failure or support.
    Logging must be sufficiently detailed to diagnose cluster failures after
    the interactive session has ended.
    User-facing messages should explain the remedy and the scientific impact.
    Preserve provenance and checksums.
    Avoid hidden, magical or environment-specific defaults.


5.2 Python
----------

    Python is the preferred implementation language where appropriate.
    Follow PEP 8.
    Use a 100-character maximum line length.
    Use Google-style docstrings for public modules, classes and functions.
    Use type hints where they improve clarity and validation.
    Prefer keyword arguments for public Python APIs.
    Validate enums, bounds, paths, schemas and non-empty inputs.
    Use the logging module rather than ad hoc diagnostic printing.
    Avoid shell interpolation when executing external commands; use argv lists.
    Use bound SQL values for user input.
    Allowlist or safely quote SQL identifiers.
    Use branch-aware coverage gates in package test runners.
    Current app test target is at least 95% branch-aware coverage.
    Workflow history used at least 90%; do not reduce an existing package gate.


5.3 R
-----

    R is appropriate for Shiny, duckplyr and existing Expression Atlas code.
    R functions also require unit tests.
    Keep SQL generation explicit and defensively quoted.
    Keep large filtering and aggregation inside DuckDB rather than collecting
    unbounded relations into R.
    Use bounded result tables.
    Preserve logical, numeric and character types where possible; when joining
    unlike schemas for display, cast deliberately and document that choice.
    Use testthat for unit and integration tests.
    Keep UI modules separate from query/scientific helpers.
    Scientific calculations belong in workflow or tested helper layers, not in
    opaque reactive expressions.


5.4 Shell
---------

    Do not embed Python programs inside shell scripts.
    Put substantive Python in separate, importable, tested Python files.
    User-facing commands should use named options, not unexplained positional
    arguments, except where an established shell tool requires them.
    Use set -euo pipefail where appropriate.
    Resolve Conda explicitly and log the environment/package actually used.
    Prefer conda run for batch jobs where activation state will not survive.
    Quote paths, especially paths containing spaces such as /Volumes/One Touch.
    Validate paths and targets before any destructive or expensive operation.
    Do not hide failed command output.
    Shell syntax checks are part of the release gate.


5.5 Outputs and file formats
----------------------------

    Do not create comma-separated analytical output files.
    Use TSV for human-readable analytical tables and manifests.
    Use Parquet for large portable typed tables.
    Use DuckDB for integrated and one-to-many relational evidence.
    Use Excel as a formatted decision/review export when requested.
    Use FASTA for raw or aligned sequence export.
    Use PDF for publication/review graphs and printable visualisations.
    Use HTML for self-contained interactive scientific review.
    Use JSON where machine-readable structured provenance is appropriate.
    Retain exact numeric data in downloads; display rounding must not mutate the
    underlying values.


5.6 Language and documentation
------------------------------

    Use UK English in user-facing prose where practical.
    Explain specialist terms in plain language.
    Keep README usage current with code.
    Provide examples with sensible defaults.
    Every release needs release notes and a validation/test status record.
    Handover documents must say what was actually tested and what could not be
    tested in the build environment.
    Never claim a test suite passed if it could not be executed.


5.7 Safety and restartability
-----------------------------

    Never treat file existence alone as completion.
    Validate declared non-empty outputs and their schemas.
    Bind stage completion to configuration and input checksums.
    Publish atomically from staging directories.
    Retain failed attempts for diagnosis.
    Preserve checksum-valid upstream work when downstream work fails.
    Support safe resume.
    Do not rewrite an immutable completed run into a scientifically different
    run.
    Create a new run name/configuration for different inputs or methods.
    Never overwrite the authoritative Results_Feb26 OrthoFinder result.

6. SCIENTIFIC DEFINITIONS AND NON-NEGOTIABLE INTERPRETATION BOUNDARIES
===============================================================================

6.1 DeepClust cluster
---------------------

A DeepClust cluster is a non-phylogenetic sequence-similarity neighbourhood
from the discovery branch. A cluster linked to a controlled E3 seed is useful
candidate evidence. It does not prove that all cluster members are E3 ligases.

Do not call DeepClust membership orthology. Do not silently merge a cluster ID
and a HOG/orthogroup ID into one concept.


6.2 Original OrthoFinder orthogroup (OG...)
-------------------------------------------

The original MCL-based OrthoFinder grouping is represented by identifiers such
as OG0001686 and the relation orthogroup_membership. It is retained as a broad
legacy/comparison grouping level.


6.3 Root-level phylogenetic hierarchical orthogroup (N0.HOG...)
----------------------------------------------------------------

The recommended final grouping is the root-level hierarchical orthogroup from:

    Phylogenetic_Hierarchical_Orthogroups/N0.tsv

It uses identifiers such as N0.HOG0002084 and the relation
hierarchical_membership. The applications expand HOG as hierarchical
orthogroup and explain that this grouping reconciles rooted gene trees with the
species tree.

HOG membership is computational evolutionary evidence. It is not experimental
proof of function, E3 activity or identical substrate specificity.


6.4 Human-containing HOG
------------------------

For application v0.13.0/v0.10.0, a human-containing HOG is strictly:

    a root-level group_id beginning N0.HOG;
    in hierarchical_membership;
    with at least one member whose source species label is Homo_sapiens.

This definition is independent of candidate ranking. Therefore all qualifying
HOGs are retained, including groups which were not candidate-ranked.


6.5 Plant-and-human HOG
-----------------------

This is a human-containing root-level HOG which also contains at least one
member whose source species label has role target_plant in the packaged
species_taxonomy.tsv manifest.

At this release, 12 source labels have target_plant role. The definition uses
the curated manifest rather than assuming that every non-human OrthoFinder
input is a target plant.


6.6 E3 seed
-----------

An E3 seed is a controlled identifier with prior evidence used to drive or
interpret discovery. A seed-linked group is important evidence. A non-seed
member of that group is not automatically an experimentally confirmed E3, and
an unseeded group member is not automatically non-E3.


6.7 Domain evidence
-------------------

Domain states must distinguish at least:

    SUPPORTED
    ANNOTATED_NO_CATALOGUED_E3_DOMAIN
    ANNOTATION_UNAVAILABLE

Only the second is an assessed negative for the reviewed domain catalogue.
Unavailable annotation is not failure.


6.8 Expression evidence
-----------------------

Expression is transcript evidence. It is not proof of protein abundance,
activity, ligase function or suitability for degradation.

The resource distinguishes mapped support, limited/zero measurements, mapping
failure and unavailable resources. Missing or unmapped evidence must not be
plotted or counted as measured zero.

Volcano plots require real differential-expression effect sizes and real
P/FDR/Q fields. Absolute Expression Atlas values must never be converted into a
fake volcano analysis.


6.9 Predicted structures and pockets
------------------------------------

AlphaFold confidence, fpocket/P2Rank scores and pocket conservation are
computational evidence. They do not prove ligand binding, selectivity,
biochemical function or induced degradation.

The embedded 3D review is a compact C-alpha trace and pocket-residue view, not
an atomistic docking environment.


6.10 Structural alignment
-------------------------

Equivalent overall fold, equivalent 3D pocket position and conserved local
pocket structure are related but different conclusions. US-align and TM-align
evidence should remain separately auditable.

Groups lacking enough compatible structures are NOT_ASSESSED, not structurally
dissimilar.


6.11 Ranking
------------

The definitive candidate authority is one row per evolutionary group. Slider
results and alternative weighting are explicitly sensitivity analyses. They do
not rewrite the official table, pipeline, configuration or database.

Absence from candidate ranking means NOT_IN_CANDIDATE_RANKING. It is not a new
biological label.

        discovery/DeepClust and 1KP coverage summaries.

    candidate_expression_summary
        broad candidate/member expression support.

    candidate_expression_context_summary
        normalised species/tissue/sample/condition expression context.

    ligandability and selected-pocket relations
        model, pocket score, selected pocket, coordinates and mapping evidence.

    structural alignment relations
        US-align/TM-align, pocket overlap and local structural evidence.

    computational chemistry relations
        target, pharmacophore, sensitivity, integrated evidence and optional

-------------------------------------

    provide FASTA only for rows with an actual published sequence;
    explicitly say when complete HOG membership sequences are unavailable.

Complete all-HOG FASTA publication would require a deliberate Stage 05/10 data
contract expansion and checksum/release review.

11. MISSING EVIDENCE POLICY
===============================================================================

The central rule is:

    unavailable evidence is not a biological negative and not a pass.

Domain:

    SUPPORTED
    ANNOTATED_NO_CATALOGUED_E3_DOMAIN
    ANNOTATION_UNAVAILABLE

Expression:

    mapped support;
    measured limited/zero expression;
    ambiguous/non-unique mapping;
    no mapping;
    unavailable resource.

Structure:

    assessed support;
    assessed below threshold;
    no compatible model/pocket;
    not structurally assessed.

Ranking:

    RANKED
    NOT_IN_CANDIDATE_RANKING

Fractions should use assessed denominators and expose evidence completeness
separately. A UI checkbox which requires assessable evidence may alter a
sensitivity list, but it must not rewrite the recorded scientific result.

14. NEW COMPLETE-RESOURCE SEARCH CONTRACT
===============================================================================

14.1 User input
---------------

Search accepts one or several terms separated by:

    newline
    comma
    semicolon
    tab

Spaces inside multi-word names are retained. Duplicate terms are removed
case-insensitively while input order is retained where supported.

Examples:

    Q9SA03
    N0.HOG0002084
    OG0001686
    FB27
    F-box protein 27
    cluster_123


14.2 Modes
----------

Smart

    exact or semicolon-token matching for identifier-like columns;
    literal case-insensitive contains matching for descriptive name fields.

Exact

    case-insensitive whole scalar or semicolon-list-token matches only.

Contains

    literal case-insensitive substring matching across recognised identifier and
    name fields.

No regex input is executed. Wildcards are not interpreted as SQL patterns.


14.3 Recognised field families

    accession

    gene_name(s)

The schema is discovered rather than assuming one fixed release relation.


14.4 Output provenance
----------------------

Every match records at least:

    search term
    relation
    matched column(s)
    all source columns from the matching row

The output has a summary table and a complete source-row table. Both are
downloadable as TSV and formatted Excel.


14.5 Safety and type behaviour
------------------------------

Python uses bound search values and safely quoted/allowlisted identifiers.

R builds escaped literal conditions and casts every returned source field to
VARCHAR before combining unlike relations. That cast is intentional: it
prevents dplyr/vctrs failures such as combining logical and character columns
with the same name from different source relations. Search is a display/audit
result, not a typed analytical calculation.

Per-relation and total result limits are enforced.

22.4 App source modes differ in capability
------------------------------------------

The one-master-Parquet mode cannot recreate detailed one-to-many memberships,
aliases, pockets or residues that are absent from that Parquet. The UI should
show a clear unavailable message, not fail or invent detail.


22.5 Search is schema-discovered, not semantic AI search
--------------------------------------------------------

Search checks recognised fields using exact/token/literal contains rules. It
does not perform fuzzy ontology expansion, synonym inference beyond published
aliases, or remote database lookup.


22.6 Applications are read-only
-------------------------------

They do not rerun domain, expression, structure, alignment or chemistry stages.
Slider calculations use stored evidence and documented gates.


22.7 Predictions are not experimental claims
---------------------------------------------

The complete resource remains computational. It does not establish E3
activity, compound binding, substrate specificity or induced degradation.
