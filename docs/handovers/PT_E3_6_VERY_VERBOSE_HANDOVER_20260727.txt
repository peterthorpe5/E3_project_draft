1.3 The latest stage-07 failure is not yet proven to be a Python logic error
-------------------------------------------------------------------------------

    Stage: 07_expression
    Run mode: production
    Evidence mode: reuse
    threads=16
    memory_mb=64000
    runtime_minutes=1440

and then ends after:

    Using the package's validated internal implementation for this stage.

Unlike the earlier, well-diagnosed failures, it does not record:

    Failed-stage resources retained: ...
    ERROR: ...

This is an important diagnostic signature. A normal StageError or DuckDB error
would pass through the workflow exception handling and should produce an
explicit message. The abrupt end instead suggests that the process was
terminated outside the normal Python error path.

The leading hypothesis is Slurm out-of-memory termination while stage 07 scans,
joins, de-duplicates and re-scans the existing Expression Atlas Parquet
resources. This is a reasoned hypothesis, not yet a confirmed fact.

Other possible external causes are:

    NODE_FAIL
    PREEMPTED
    CANCELLED
    a signal from the scheduler or operating system
    a filesystem or worker-node failure that prevented normal error logging

The exact Slurm job state and worker log must be captured before another blind
rerun.

2. PROJECT IDENTITY, PURPOSE AND SCIENTIFIC BOUNDARIES
===============================================================================

Project:

    PT_E3_6 / ARIA plant E3 project

Primary repository:

    https://github.com/peterthorpe5/E3_project_draft

Primary Dundee project root:

    /home/pthorpe001/data/2026_E3_protac

Equivalent GPFS path used in logs:

    /gpfs/uod-scale-01/cluster/gjb_lab/pthorpe001/2026_E3_protac

The project builds a modular, restartable and extensible computational
resource for plant E3-ligase discovery and ligandability prioritisation. The
immediate work supports the grant milestones, but the implementation must
remain species-count agnostic and suitable for later expansion to much larger
proteome panels.

Scientific boundaries that must be retained:

1. A sequence cluster containing a controlled E3 seed is candidate evidence.
   It does not prove that every cluster member is an E3 ligase.

2. An OrthoFinder orthogroup or hierarchical orthogroup is run-specific
   computational evidence. It is not experimental proof of orthology.

3. “HOG” should be avoided in explanatory prose and user-facing labels.
   Prefer “hierarchical orthogroup”.

4. Expression evidence is transcript context. It is not protein activity.

5. Missing expression or domain coverage must be represented as unavailable,
   not as a biological zero or negative.

6. Predicted pockets and structural similarity do not prove binding,
   selectivity, target degradation or biochemical function.

7. Structural alignment is supporting evidence. It must not be used for
   prioritisation until thresholds have been reviewed on an appropriate
   multi-structure dataset.

8. DeepClust sequence clusters and OrthoFinder groups are different scientific
   entities and must never be described as interchangeable.

3. SOFTWARE AND DATA-ENGINEERING REQUIREMENTS
===============================================================================

These requirements should be treated as standing project constraints.

Python:

    preferred implementation language;
    PEP 8;
    100-character line length;
    Google-style docstrings;
    defensive validation;
    explicit logging;
    type-aware, maintainable functions;
    unit tests for every function where practical;
    end-to-end tests for publication boundaries and complete workflows;
    branch-aware coverage target of at least 90%.

R:

    acceptable where it is the natural implementation, especially the existing
    Expression Atlas and Shiny components;
    tests are required;
    resource paths and analytical transformations must remain explicit.

Shell:

    user-facing entry points should use named arguments;
    do not embed Python programs inside shell scripts;
    resolve the Conda executable and environment explicitly;
    on Dundee Slurm, prefer conda run or source a valid conda.sh before using
    conda activate;
    log the resolved Python and package version;
    use set -euo pipefail where appropriate;
    validate paths before destructive or expensive work.

Outputs:

    analytical tables should be TSV, Parquet or DuckDB;
    do not create comma-separated analytical output files;
    use TSV for human-auditable reports and manifests;
    use Parquet for large portable tables;
    use DuckDB for integrated one-to-many evidence;
    use HTML for scientific and operational reports.

Restartability:

    never treat output-file existence as proof of success;
    validate expected outputs;
    bind completion to the configuration and input checksums;
    publish atomically from a temporary staging directory;
    retain failed attempts for diagnosis;
    record success, failure and partial states;
    support --resume, --start-at, --stop-after and --force-stage;
    preserve earlier valid stages when a downstream stage fails.

Slurm:

    account: barton
    partition: general
    cluster maximum runtime: 3 days / 4,320 minutes
    complete fresh runs may use 32 cores where appropriate
    up to 10 concurrently submitted scientific jobs is acceptable
    the Snakemake controller should itself be submitted with sbatch
    the workflow must remain usable on non-Slurm systems

4.4 expression_downloader
-------------------------

Purpose:

    discover and download Expression Atlas experiments;
    create partitioned long-form Parquet;
    create metadata Parquet;
    create DuckDB views;
    skip existing non-empty resources unless forcing is explicit.

The end-to-end stage consumes a checksum-controlled resource manifest. It
should not rerun the downloader merely because a new candidate set is being
analysed.


4.5 e3_ligandability_pipeline
-----------------------------

Purpose:

    AlphaFold model confidence;
    FPocket and P2Rank pocket evidence;
    residue mapping;
    pocket quality and conservation support.

Important limitation:

    predicted pockets are not evidence of experimental binding or degradation.


4.6 e3_structural_alignment
---------------------------

Purpose:

    optional US-align/TM-align direct 3D comparisons;
    assess whether candidate pockets occupy similar structural positions;
    map pocket residues back to sequence indices;
    support interactive and static review outputs where possible.

This remains optional for the current run. Missing compatible structures must
be represented as NOT_ASSESSED rather than structural dissimilarity.


4.7 e3_end_to_end_workflow
--------------------------

Purpose:

    own the Snakemake DAG;
    validate configuration and inputs;
    run component adapters;
    manage stage restart state;
    validate declared outputs;
    aggregate resources;
    produce reports;
    publish application hand-off configuration.

-----------------

Purpose:

    read-only Streamlit exploration of completed integrated resources.


4.9 E3_shiny_app
----------------

Purpose:

    read-only R Shiny exploration of the same integrated resource;

5. END-TO-END STAGES
===============================================================================

00_inputs

    Validate controlled inputs and record checksums.

01_prepared_proteomes

    Validate, isolate and standardise included complete proteomes.

02_discovery

    Run or reuse controlled E3-seed discovery.

03_candidate_evidence

    Build or reuse candidate-cluster evidence.

04_orthofinder

    Run fresh OrthoFinder or validate/reuse the authoritative result.

05_orthology

    Reconcile identifiers and publish candidate-relevant group membership and
    sequences.

06_domains

    Obtain/reuse InterPro and Pfam annotations, cache responses, and represent
    unavailable annotation explicitly.

07_expression

    Map selected group members to existing Expression Atlas resources and
    build run-specific summaries.

08_shortlist_gate

    Apply transparent computational prioritisation and publish the structural
    analysis input set.

09_ligandability

    Reuse or generate structure/pocket evidence and assess pocket-region
    conservation.

09b_structural_alignment

    Optional 3D pocket-position and structural-conservation evidence.

10_integrated_resource

    Create integrated DuckDB, Parquet, TSV and scientific report outputs.

11_app_ready

    Publish Python and Shiny application hand-off configuration.

Independent branches may run concurrently after their prerequisites. In
particular, 06_domains and 07_expression can run concurrently after
05_orthology.

12. STAGE-07 DIAGNOSIS
===============================================================================

12.1 What the missing error line means
--------------------------------------

Earlier failures followed the normal Python error path.

For example, the duplicate-orthology-file failure recorded:

    Failed-stage resources retained: ...
    ERROR: Expected exactly one ...

The latest failure records neither line.

The stage runner normally measures resources, catches a recognised workflow
error, retains failed-stage information, and prints an ERROR message. An abrupt
end before that handling strongly suggests:

    SIGKILL or another external signal;
    Slurm/operating-system termination;
    node-level failure;
    or another event that prevented Python cleanup and logging.


12.2 Why out-of-memory is the leading hypothesis
------------------------------------------------

The existing expression manifest covers the previously downloaded Atlas
resource. The audited resource set was reported as approximately:

    778 manifest rows;
    387 atlas_expression_long resources;
    195 atlas_sample_metadata_long resources;
    195 atlas_sample_metadata_wide resources;
    23 species partitions.

Stage 07 uses the 387 expression-long Parquet paths.

The implementation:

1. verifies resource checksums;
2. reads all configured expression-long paths with DuckDB;
3. creates aliases for all selected group members;
4. joins aliases to expression rows using upper-cased species and identifier
   comparisons;
5. allows matching on gene_id OR gene_name;
6. materialises DISTINCT alias/gene matches;
7. builds mapping and expression summaries;
8. performs grouped counts, fractions, medians and string aggregations;
9. exports Parquet; and
10. re-executes queries to retrieve rows for TSV output.

The current implementation can scan the Atlas resource repeatedly:

    once to create alias_gene_matches;
    again while producing the expression summary Parquet;
    again when retrieving expression summary rows for TSV.

The use of upper(CAST(...)) and an OR condition across gene_id and gene_name can
also make predicate pushdown and efficient joins harder.

The job was allocated 64,000 MiB. A kill during this work, without a caught
DuckDB error, is consistent with a Slurm out-of-memory event.


12.3 Why out-of-memory is not yet confirmed
-------------------------------------------

The supplied log does not contain:

    OUT_OF_MEMORY
    oom-kill
    Killed
    ExitCode=137
    signal 9

Those details normally come from:

    sacct
    the Slurm worker log
    slurmstepd stderr
    the detailed Snakemake job log

Until those are inspected, describe the cause as:

    probable external termination;
    memory exhaustion is the leading hypothesis.


12.4 Alternative interpretations
--------------------------------

If sacct says:

then stage 07 needs a scalability correction. Raising memory alone may hide,
rather than solve, repeated full-dataset scans.

If sacct says:

not copied into the persistent excerpt.

If the exit code includes:

14.1 Restrict the resource before expensive joins
-------------------------------------------------

14.2 Normalise once
-------------------

Create normalised alias keys once:

    upper-case species key
    upper-case gene/accession key
    identifier type

14.3 Separate gene-ID and gene-name joins
-----------------------------------------

Instead of one large join containing:

    gene_id match OR gene_name match
